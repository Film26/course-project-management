## 1. Linked requirements (summary — full text in `docs/srs.md`)

| ID | Requirement / rule |
|---|---|
| FR-10 | A Student can create a team in a course and receives a join code. |
| FR-11 | A Student can join a team using its join code. |
| FR-12 | A Student can leave their team while the team has no approved proposal. |
| BR-06 | A student belongs to at most one team per course. |
| BR-07 | Team size is between the course's `minTeamSize` and `maxTeamSize` (default 2–3); joining a full team is rejected; a proposal can be submitted only when the team has at least `minTeamSize` members. |
| BR-08 | Team membership is locked once the team's proposal is `APPROVED`. |
| NFR-02 / NFR-03 | 401 without a session; 403 for a forbidden role or course; no team data in the body. |
| NFR-05 | Errors use `{error:{code,message,details?}}`. |
| NFR-06 | A rejected request never leaves partial data; BR-06 is also a DB unique constraint. |
| NFR-09 | Team screens have loading, empty and error states. |

## 2. Behaviour and workflow

```
 Student enrolled in course, no team                Student in a team
 ┌───────────────────────────────────────┐   ┌───────────────────────────────────────────┐
 │ create team (name) ─► new team,       │   │ sees team, members, join code             │
 │   creator is first member, join code  │   │ leave ─► removed (BR-08: not if APPROVED) │
 │ join (code) ─► member (BR-06, BR-07)  │   │ submit proposal ─► F-02 + BR-07 min size  │
 └───────────────────────────────────────┘   └───────────────────────────────────────────┘
```

### Business rules as implemented
- **T1 Enrollment.** A new `Enrollment(courseId, userId)` table says which students belong to a course (until now this was implied by team membership). Only an enrolled STUDENT can create or join a team in that course; otherwise 403. The migration enrolls every existing team member, so no current user loses access.
- **T2 (BR-06)** Create or join is rejected with `409 ALREADY_IN_TEAM` when the student already has a team in the course. Backed by a DB unique constraint `TeamMember(courseId, userId)`; a unique-violation from a race is mapped to the same 409.
- **T3 (BR-07, join)** Join runs in one transaction that locks the team row (`SELECT … FOR UPDATE`) and counts members. `count >= course.maxTeamSize` → `409 TEAM_FULL`. Boundary: joining as the `maxTeamSize`-th member is accepted.
- **T4 (BR-07, submit)** Proposal submit (F-02) additionally requires `memberCount >= course.minTeamSize`, otherwise `409 TEAM_TOO_SMALL` and the proposal stays `DRAFT`. Checked after the F-02 transition and deadline checks. Boundary: exactly `minTeamSize` members is accepted. Recorded as F-02 contract v1.3.
- **T5 (BR-08)** Join and leave are rejected with `409 MEMBERSHIP_LOCKED` when the team has an `APPROVED` proposal. A `REJECTED`, `DRAFT` or `SUBMITTED` proposal does not lock the team.
- **T6 (FR-12)** When the last member leaves, the team is deleted if it has no proposals; a team with proposals is kept with no members (proposal history, D-05).
- **T7 (FR-10)** The join code is 8 characters from `A–Z` and `2–9` without `O`, `I`, `0`, `1`, generated in the database by `cpms_join_code()` as the column default *(v1.1)*, unique across all teams (DB unique index; on a collision the service retries the insert up to 5 times). Codes are compared after trim + upper-case. Only members of the team and the course instructor see the code.
- **T8** Team names are unique per course (existing `@@unique([courseId, name])`); a duplicate → `409 TEAM_NAME_TAKEN`.
- **T9** The acting user always comes from the session. `userId`, `teamId` or `courseId` in a body are ignored.

### Validation
| Field | Rule | Error |
|---|---|---|
| `name` (create) | required; string; trimmed; 1–60 chars | 400 `VALIDATION_ERROR`, `details.name` |
| `joinCode` (join) | required; string; after trim + upper-case matches `^[A-HJ-NP-Z2-9]{8}$` | 400 `VALIDATION_ERROR`, `details.joinCode` |
| path ids | positive integers | 400 `VALIDATION_ERROR` |

A well-formed code that matches no team **in this course** → `404 NOT_FOUND` (the response does not say whether the code exists in another course).

## 3. API contract

All endpoints require a session (`401 UNAUTHENTICATED`). Order of checks: authenticate (401) → role (403) → validate (400) → load resource (404) → enrollment/membership (403) → business rule (409) → write.

**Team object** (`T`): `{ id, name, courseId, joinCode, members: [ { id, displayName } ], memberCount, locked }` (`locked` = BR-08)

| Method & path | Who | Request | Success | Errors |
|---|---|---|---|---|
| `POST /api/courses/:courseId/teams` | STUDENT, enrolled | `{ name }` | `201 { team: T }`, creator is the only member | 400, 403, 404, 409 `ALREADY_IN_TEAM`, 409 `TEAM_NAME_TAKEN` |
| `POST /api/courses/:courseId/teams/join` | STUDENT, enrolled | `{ joinCode }` | `200 { team: T }` | 400, 403, 404, 409 `ALREADY_IN_TEAM`, 409 `TEAM_FULL`, 409 `MEMBERSHIP_LOCKED` |
| `POST /api/teams/:teamId/leave` | STUDENT, member | — | `200 { left: true, teamDeleted: boolean }` | 400, 403, 404, 409 `MEMBERSHIP_LOCKED` |
| `GET /api/courses/:courseId/my-team` *(changed)* | STUDENT, enrolled | — | as F-02, plus `team.joinCode`, `team.locked`, `course.minTeamSize`, `course.maxTeamSize` | 403 not enrolled *(was 404)*, 404 no team |
| `GET /api/courses` *(changed)* | any | — | STUDENT: courses where **enrolled** (was: where in a team). Instructor unchanged | — |
| `GET /api/courses/:courseId/roster` *(changed)* | INSTRUCTOR, owns course | — | as F-01, plus `team.joinCode` and `unassigned: [ { id, displayName, email } ]` (enrolled, no team) | as F-01 |
| `POST /api/proposals/:id/submit` *(changed)* | as F-02 | — | as F-02 | as F-02 + 409 `TEAM_TOO_SMALL` |

### Application-layer components (server)
| Module | Responsibility |
|---|---|
| `src/teams/rules.js` | Pure logic: `validateTeamName(body)`, `normalizeJoinCode(body)`, `canJoin(memberCount, maxTeamSize)`, `hasMinimumSize(memberCount, minTeamSize)`, `isMembershipLocked(proposalStatuses)` *(v1.1: no code generator; see T7)* |
| `src/teams/service.js` | Transactions with team row lock, enrollment and membership look-ups, unique-violation → 409 mapping, empty-team clean-up (T6) |
| `src/routes/teams.js` | `POST /api/courses/:courseId/teams`, `/teams/join`, `POST /api/teams/:teamId/leave` |
| `src/proposals/service.js` | `submitProposal` adds the T4 size check (F-02 v1.3) |

## 4. Data

Migration `20261125060000_f03_team_formation` *(v1.1)*:
- `Course.minTeamSize Int @default(2)`, `Course.maxTeamSize Int @default(3)`; SQL `CHECK (1 <= "minTeamSize" AND "minTeamSize" <= "maxTeamSize")`.
- SQL function `cpms_join_code()`; `Team.joinCode String @unique @default(dbgenerated("cpms_join_code()"))` (existing rows get a code from the default), `Team.createdAt DateTime @default(now())`.
- New `Enrollment { courseId, userId, enrolledAt }`, `@@id([courseId, userId])`, FKs cascade. Back-filled from existing `TeamMember` rows.
- `TeamMember.courseId Int` (FK `Course`, back-filled from `Team.courseId`), `TeamMember.joinedAt DateTime @default(now())`, `@@unique([courseId, userId])` (BR-06 in the DB).
- **Seed change:** adds `student4` (into Team Beta, so Beta has 2 members = `minTeamSize`), `student5` and `student6` (enrolled, no team). All six students are enrolled in CPE334. Team Alpha and Team Beta get fixed join codes in the seed (`ALPHA234`, `BETA2345`) so tests and UAT can use them.

## 6. Acceptance criteria

| AC | Given / When / Then | Reqs |
|---|---|---|
| AC-03-01 | Given an enrolled student without a team, when they create a team with a valid name, then 201, they are its only member, the team has an 8-character join code, and one team and one membership row are stored. | FR-10 |
| AC-03-02 | Missing, blank or > 60-char team name → 400 `VALIDATION_ERROR` (`details.name`); a name already used in the course → 409 `TEAM_NAME_TAKEN`; no row is stored. | FR-10, NFR-05 |
| AC-03-03 | Given an enrolled student without a team, when they join with a valid code of a team in the course that is below `maxTeamSize`, then 200 and the membership is stored. A lower-case code with spaces around it is accepted. | FR-11 |
| AC-03-04 | A student who already has a team in the course cannot create or join another team: 409 `ALREADY_IN_TEAM`, no row changed. Two concurrent joins by the same student store at most one membership. | BR-06, NFR-06 |
| AC-03-05 | Joining a team that already has `maxTeamSize` members → 409 `TEAM_FULL`. Joining as the `maxTeamSize`-th member is accepted. Two concurrent joins for the last place: exactly one succeeds. | BR-07, NFR-06 |
| AC-03-06 | A malformed code → 400 (`details.joinCode`); a well-formed code with no team in this course (including a code of another course's team) → 404; no row changed. | FR-11 |
| AC-03-07 | A member leaves a team with no approved proposal → 200; the membership is removed. When the last member leaves, the team is deleted if it has no proposals and kept if it has any. | FR-12 |
| AC-03-08 | When the team's proposal is `APPROVED`, join and leave → 409 `MEMBERSHIP_LOCKED`; membership unchanged. A team whose only proposal is `REJECTED` is not locked. | BR-08 |
| AC-03-09 | Submitting a `DRAFT` proposal with fewer than `minTeamSize` members → 409 `TEAM_TOO_SMALL`; the proposal stays `DRAFT` with `submittedAt = null`. With exactly `minTeamSize` members the submit succeeds. | BR-07, FR-06 |
| AC-03-10 | An instructor cannot create, join or leave (403). A student not enrolled in the course cannot create or join (403) or read `my-team` (403). A student cannot leave a team they are not in (403). No team data in any 403 body. | NFR-03 |
| AC-03-11 | All F-03 endpoints without a session → 401 `UNAUTHENTICATED`. | NFR-02 |
| AC-03-12 | Members see their team with members and join code via `my-team`; the course instructor sees join codes and unassigned students in the roster; a student in another team never sees this team's code. | FR-10, FR-04 |
| AC-03-13 | UI journey: student5 creates "Team Gamma" and sees the code; student6 joins with that code; both see 2 members; student6 leaves; student5 sees 1 member and the submit warning. | FR-10–FR-12, NFR-09 |
